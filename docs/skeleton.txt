You are the orchestrator for scaffolding a walking skeleton of GameGPT, a cross-platform game discovery app. You will delegate implementation to subagents via the Task tool. Read this entire brief before doing anything.

## The product

Users link gaming accounts (Steam, Xbox, Epic) to build a cross-platform library. They type a natural language query like "a chill game I can play while listening to a podcast." A RAG pipeline embeds the query, runs semantic search over a game metadata knowledge base, filters out games the user already owns, and passes candidates to an LLM that returns 3 to 5 ranked recommendations with explanations. Users leave thumbs up/down feedback that adjusts future ranking.

## Scope of this skeleton — read carefully

Build exactly one vertical slice, end to end:

query box → `POST /api/recommend` → embed query → vector top-k → drop owned games → LLM ranks 3 → persist query + recommendations → render cards → thumbs up/down → `POST /api/feedback`

Everything on this list is **explicitly out of scope**. Do not build it, do not stub elaborate versions of it, do not add placeholder UI for it:

- Google OAuth or any real auth. Use a single seeded dev user with a hardcoded UUID in env.
- Xbox and Epic integration.
- Game detail pages, purchase links, recommendation history pages, pagination.
- Feedback affecting ranking. Persist feedback only.
- Styling beyond legible defaults. No design system, no component library.

Steam is the one integration to build for real: `IPlayerService/GetOwnedGames` needs only an API key and a public steamID64, no OAuth. Expose it as `POST /api/library/sync` behind a text input where the user pastes a Steam ID. If the Steam key is absent from env, fall back to seeded library rows so the slice still runs.

## Stack

- API: Python 3.12, FastAPI, Pydantic v2, uv for deps
- DB: Supabase Postgres, SQL migrations under `/supabase/migrations`
- Vectors: pgvector on Supabase. Do **not** use Pinecone in the skeleton — one fewer service to provision, and the interface is behind `VectorStore` so it can be swapped later.
- LLM + embeddings: Anthropic for generation, OpenAI `text-embedding-3-small` for embeddings. Both behind service interfaces.
- Web: Next.js App Router, TypeScript, minimal Tailwind
- Deploy: Render for the API, Vercel for the web app. Deployed and reachable over HTTPS from Phase 0, before any real logic exists.

`api/services/` must contain one module per block in the team's SysML structure diagram, with these exact names, each a class with a narrow interface: `EmbeddingService`, `VectorStore`, `LLMService`, `DeduplicationService`, `RAGPipeline`, `LibrarySyncService`. Traceability from the diagram to the code is a grading criterion, so do not rename or merge them.

## Phase 0 — deploy a fake, first

Nothing real ships in this phase. The deliverable is a URL a stranger can open on a phone. Every later phase replaces fakes behind an interface that is already live in production.

Build:

No DB, no LLM, no vector store, no Steam.

## Phase 1 — contract and foundations, you do this yourself, no subagents

Shared foundations. Subagents working in parallel on these would conflict.

1. Repo skeleton, `.gitignore`, `README.md`, `.env.example` (never a real `.env`, never a real key anywhere).
2. SQL migration defining: `users`, `games`, `platform_accounts`, `owned_games`, `queries`, `recommendations`, `recommendation_feedback`. `games` carries title, description, genres[], tags[], release_date, developer, review_score, steam_appid, and a `vector(1536)` embedding column. Enable pgvector. Seed one dev user.
3. Pydantic models in `api/models/` for every request and response body, and the service interfaces as abstract base classes in `api/services/` with `NotImplementedError` bodies and full type hints.
4. `api/main.py` with `/api/health` and CORS wired for `localhost:3000`.
5. Commit. This is the contract every subagent codes against.

Then generate `openapi.json` and hand its path to the frontend agent.

## Phase 2 — four parallel subagents

Launch all four in a single message so they run concurrently. Each subagent gets: this brief, the contract files from Phase 1, and a hard file-ownership boundary. State in each subagent's prompt that it must not create or edit files outside its owned paths, and must report any needed change to a contract file back to you instead of making it.

**Agent A — data and seeding.** Owns `/scripts`, `/supabase/seed.sql`. Writes `seed_games.py` to pull 150 games from the RAWG API (key from env, and a committed JSON fixture fallback so the pipeline runs with no key) and insert into `games`. Writes `embed_games.py` to embed `title + description + genres` and write the vector column in batches with retry. Both scripts idempotent and re-runnable.

**Agent B — RAG pipeline.** Owns `api/services/*` implementations. Concrete `EmbeddingService`, `VectorStore` (pgvector cosine top-k, k=20), `LLMService` (Anthropic call, structured JSON out, validated against the Pydantic model, one retry on parse failure), `DeduplicationService` (drop candidates present in `owned_games` for that user, matching on `steam_appid` first and normalized title second), `RAGPipeline` orchestrating the five. Unit tests with the LLM and embedding calls faked.

**Agent C — routers and persistence.** Owns `api/routers/*`, `api/db/*`. Implements `/api/recommend`, `/api/feedback`, `/api/library`, `/api/library/sync` against Agent B's interfaces, not its implementations. Persists each query and its recommendations. Real Steam Web API call in `LibrarySyncService`'s caller path. Structured error responses, retry up to two times on DB failure per the team's rainy-day scenarios.

**Agent D — frontend.** Owns `/web`. Generates TypeScript types from `openapi.json`, a typed fetch client in `web/lib/api/`, one page with the query input, a loading state, three result cards showing title, reason and rank, and thumbs up/down wired to `/api/feedback`. A Steam ID input calling `/api/library/sync`. Mock Service Worker or a simple fixture mode so it develops without a running API.

## Rules for the whole run

- No secrets in any committed file. `.env.example` with empty values only.
- Prefer fewer files over more. No abstraction that has exactly one caller and no second caller planned.
- Every external call goes behind a service class so it can be faked in tests.
- If a subagent reports that the Phase 0 contract is wrong, change it yourself, commit, and tell the affected agents. Do not let two agents edit a model.
- Commit at the end of each phase with a message naming what landed.
